Objet et périmètre

Le tableau de bord estime l'empreinte carbone de l'inférence des modèles utilisés via GitHub Copilot, jour par jour, à partir de l'export « AI usage report ». Il applique la méthode « Contrôle des tokens GitHub Copilot pour l'empreinte carbone de l'inférence » du 20 octobre 2026.

The dashboard estimates the carbon footprint of inference for the models used through GitHub Copilot, day by day, from the “AI usage report” export. It applies the method “GitHub Copilot token controls for the carbon footprint of inference” of 20 October 2026.

  • Inclus : les tokens facturés en crédits IA (Copilot Chat, CLI, agent cloud, Spaces, Spark, agents tiers, revue de code) et l'énergie de l'inférence côté fournisseur.
  • Exclus : les complétions de code (non facturées en crédits, donc absentes de l'export), le réseau et les postes de travail. La fabrication du matériel est exclue par la méthode ; elle n'intervient ici que dans le calcul de repli du Calculateur de Boris, si l'option est cochée.
  • Les règles de facturation servent à reconstituer des volumes sans double comptage, jamais comme facteur physique. La remise de 10 % de la sélection automatique ne réduit pas l'empreinte : les tokens traités sont les mêmes.
  • Included: tokens billed in AI credits (Copilot Chat, CLI, cloud agent, Spaces, Spark, third-party agents, code review) and the provider-side energy of inference.
  • Excluded: code completions (not billed in credits, so absent from the export), the network and workstations. Hardware manufacturing is excluded by the method; here it only enters Boris's calculator fallback calculation, if the option is ticked.
  • Billing rules are used to rebuild volumes without double counting, never as a physical factor. The 10% auto-selection discount does not reduce the footprint: the processed tokens are the same.

Étapes de calcul

  1. Input frais : F = I − δ·CR − ε·CW. I est la colonne input brute ; δ et ε indiquent si elle contient déjà le cache lu et le cache écrit.
  2. Tokens équivalent output : T_O = F·s_I + CR·s_CR + CW·s_CW + O. Chaque catégorie de tokens est pondérée par son prix rapporté au prix de l'output du même modèle (s_I = P_I / P_O, etc.).
  3. Énergie : E = T_O × e_O × PUE / 1000, avec e_O l'énergie par token généré (Wh) issue d'EcoLogits v2 via le Calculateur de Boris : énergie GPU + énergie serveur par token, pour le scénario EcoLogits rattaché au modèle (le plus proche par taille et par prix quand le modèle n'existe pas dans le Calculateur de Boris), et PUE de 1,2. Ces kWh ne dépendent pas de votre table de facteurs : ils alimentent la tuile Énergie et l'équivalence en recharges de smartphone, et restent indicatifs.
  4. Empreinte : CO₂e = T_O × FE_token, avec FE_token en kgCO₂e par token, issu de votre table de facteurs. À défaut, FE_token = e_O × PUE × FE_mix / 10⁶ (+ fabrication), soit exactement le calcul du Calculateur de Boris.
  1. Fresh input: F = I − δ·CR − ε·CW. I is the raw input column; δ and ε tell whether it already contains the cache read and the cache write.
  2. Output-equivalent tokens: T_O = F·s_I + CR·s_CR + CW·s_CW + O. Each token category is weighted by its price relative to the output price of the same model (s_I = P_I / P_O, etc.).
  3. Energy: E = T_O × e_O × PUE / 1000, where e_O is the energy per generated token (Wh) from EcoLogits v2 via Boris's calculator: GPU energy + server energy per token, for the EcoLogits scenario mapped to the model (the closest by size and price when the model does not exist in Boris's calculator), and a PUE of 1.2. These kWh do not depend on your factor table: they feed the Energy tile and the smartphone charge equivalent, and are indicative.
  4. Footprint: CO₂e = T_O × FE_token, with FE_token in kgCO₂e per token, from your factor table. Otherwise FE_token = e_O × PUE × FE_mix / 10⁶ (+ manufacturing), exactly Boris's calculator's own calculation.

Les quatre formules sont modifiables dans la vue Calcul. EcoLogits ne compte que les tokens générés : appliquer un facteur par token généré à T_O, qui intègre l'input et le cache pondérés par les prix, est une extension de méthode à déclarer.

The four formulas can be edited in the Calculation view. EcoLogits only counts generated tokens: applying a per-generated-token factor to T_O, which includes input and cache weighted by prices, is a method extension to be disclosed.

Conventions δ et ε

La valeur retenue pour chaque modèle suit cet ordre : C2 (si CR + CW dépasse I sur au moins une ligne, la convention est forcément exclusive), puis C3 (rapprochement des coûts), puis la convention documentée de l'API du fournisseur. Elle peut être forcée dans la vue Calcul.

GitHub does not document whether the export's input column already contains the cache. The value used for each model follows this order: C2 (if CR + CW exceeds I on at least one row, the convention must be exclusive), then C3 (cost reconciliation), then the provider's documented API convention. It can be forced in the Calculation view.

Facteurs d'émission par token

FE_token provient de votre table de facteurs en kgCO₂e par token (transmise le 23 octobre 2026), dont chaque ligne est marquée « Source » ou « Hypothèse ». Les modèles absents de la table sont calculés avec le carbon-footprint-modeling-tool de Boris Ruf, appelé ici « Calculateur de Boris », scénarios EcoLogits v2 (commit 50bc8b0 du 4 septembre 2026).

FE_token comes from your factor table in kgCO₂e per token (supplied on 23 October 2026), where each row is marked “Source” or “Assumption”. Models missing from the table are computed with the carbon-footprint-modeling-tool by Boris Ruf, called “Boris's calculator” here, EcoLogits v2 scenarios (commit 50bc8b0 of 4 September 2026).

Pour un modèle, le Calculateur de Boris calcule : PUE (1,2) × (énergie GPU + énergie serveur par token, en kWh) × intensité du mix électrique (France 2020, EEA, 51,1 g/kWh par défaut) + fabrication du matériel par token (scope 3). Le tableau de bord reproduit ce calcul à l'identique (écart nul vérifié sur les 34 scénarios EcoLogits v2). La plupart des modèles Copilot de 2026 n'existent pas dans le Calculateur de Boris : ils sont rattachés au scénario le plus proche par taille et par prix (« proxy »), modifiable dans la vue Calcul.

For a model, Boris's calculator computes: PUE (1.2) × (GPU energy + server energy per token, in kWh) × electricity mix intensity (France 2020, EEA, 51.1 g/kWh by default) + hardware manufacturing per token (scope 3). The dashboard reproduces this calculation exactly (zero difference checked on the 34 EcoLogits v2 scenarios). Most 2026 Copilot models do not exist in Boris's calculator: they are mapped to the closest scenario by size and price (“proxy”), editable in the Calculation view.

Contrôles

  • C1 · Complétude et périmètre : colonnes présentes, valeurs positives, dates postérieures au 1er juin 2026, modèles présents dans la grille, cohérence gross_amount = quantity × applied_cost_per_quantity.
  • C2 · Test structurel : CR + CW − I > 0 sur une ligne impose la convention exclusive pour ce modèle.
  • C3 · Rapprochement des coûts : jusqu'à 5 lignes par famille (montant ≥ 1 $, cache read élevé, Δ = C_excl / C_incl − 1 > 11 %). Le rapport R = montant facturé / coût théorique doit tomber entre 0,90 et 1,00 pour l'une des hypothèses. Le montant facturé est gross_amount (aic_gross_amount seulement si gross_amount manque) ; jamais net_amount.
  • C4 · Cas particuliers : cache write non facturé (s_CW = s_I), input frais négatif.
  • C5 · Bouclage global : Σ montant facturé / Σ coût recalculé entre 0,90 et 1,00 sur toute la période.
  • C6 · Sensibilité : convention alternative pour les familles non tranchées, facteurs bas et haut, Calculateur de Boris avec plusieurs mix, part du cache read dans T_O.
  • C1 · Completeness and scope: columns present, positive values, dates after 1 June 2026, models present in the price list, consistency gross_amount = quantity × applied_cost_per_quantity.
  • C2 · Structural test: CR + CW − I > 0 on a row forces the exclusive convention for that model.
  • C3 · Cost reconciliation: up to 5 rows per family (amount ≥ $1, high cache read, Δ = C_excl / C_incl − 1 > 11%). The ratio R = billed amount / theoretical cost must fall between 0.90 and 1.00 for one of the hypotheses. The billed amount is gross_amount (aic_gross_amount only when gross_amount is missing); never net_amount.
  • C4 · Special cases: cache write not billed (s_CW = s_I), negative fresh input.
  • C5 · Global reconciliation: Σ billed amount / Σ recomputed cost between 0.90 and 1.00 over the whole period.
  • C6 · Sensitivity: alternative convention for unsettled families, low and high factors, Boris's calculator with several mixes, cache read share of T_O.

Indicateurs de la vue Empreinte

Tous les indicateurs suivent la période et les filtres choisis, et reposent sur le résultat central (formules et paramètres de la vue Calcul).

All indicators follow the selected period and filters, and rely on the central result (formulas and parameters of the Calculation view).

  • Équivalences : CO₂e divisé par un facteur de référence. Voiture thermique moyenne, construction incluse : 0,142 kgCO₂e/km ; repas avec du bœuf : 4,97 kgCO₂e ; repas végétarien : 0,85 kgCO₂e (impactCO2, ADEME, transport ; alimentation). Recharge de smartphone : 0,019 kWh, comparée à l'énergie et non au CO₂e pour ne pas dépendre du mix américain (US EPA, Greenhouse Gas Equivalencies).
  • Intensité : CO₂e rapporté aux utilisateurs actifs, aux jours-utilisateur, au million de tokens équivalent output et au dollar brut facturé (gross_amount). L'export agrège les usages par utilisateur, modèle et jour : il ne contient pas de nombre de requêtes, d'où le jour-utilisateur comme unité d'usage.
  • Tendance : cumul jour par jour du dernier mois de la période. La projection de fin de mois ajoute au cumul à date une prévision pour chaque jour restant. Cinq méthodes sont proposées dans la vue Calcul. Par défaut, le modèle fondé sur les usages calcule chaque jour restant comme N × p × U × I : N, utilisateurs distincts sur 28 jours glissants ; p, taux d'activité selon le jour de semaine, le mois (calculé sur l'historique s'il couvre 13 mois, sinon juillet ×0,8 et août ×0,45), les jours fériés français et la semaine de Noël ; U, tokens éq. output par utilisateur actif ; I, intensité carbone du mix des 28 derniers jours. N et U prolongent leur tendance des 6 derniers mois, amortie de 10 % par mois, avec un plafond de licences optionnel. Une fourchette P10–P90 est obtenue en rejouant 400 fois les écarts observés sur les 180 derniers jours. Les autres méthodes : rythme moyen à date, rythme des N derniers jours, jours ouvrés et week-end, tendance linéaire. Un ajustement en % du reste du mois permet d'intégrer un événement connu, et un contrôle a posteriori compare chaque méthode aux mois complets précédents. La comparaison au mois précédent se fait à date équivalente, et seulement si ce mois est entièrement dans la période. L'horizon peut aussi être la fin de l'année : le cumul part du 1er janvier, ou du premier jour de la période analysée s'il est plus tardif, et la projection court jusqu'au 31 décembre.
  • Émissions jour par jour, semaine par semaine : intensité de couleur proportionnelle au CO₂e du jour, du plus faible au plus fort de la période. La colonne « Part » répartit l'empreinte par jour de la semaine.
  • Levier modèle : les lignes du modèle actuel sont recalculées comme si le modèle cible les avait traitées, avec les mêmes tokens input, output, cache read et cache write, mais les ratios de prix, la convention δ/ε et le FE_token du modèle cible. Seuls les modèles déjà présents dans l'export sont proposés. L'écart de qualité ou de verbosité entre modèles n'est pas modélisé.
  • Fourchette d'incertitude : minimum et maximum parmi les variantes de sensibilité (FE_token × bas et × haut, Calculateur de Boris avec chaque mix électrique, convention δ/ε inversée quand elle n'est fixée que par défaut). C'est la même logique que le contrôle C6, appliquée au périmètre filtré.
  • Equivalents: CO₂e divided by a reference factor. Average combustion car, manufacturing included: 0.142 kgCO₂e/km; beef meal: 4.97 kgCO₂e; vegetarian meal: 0.85 kgCO₂e (impactCO2, ADEME, transport; food). Smartphone charge: 0.019 kWh, compared with energy rather than CO₂e so as not to depend on the US grid mix (US EPA, Greenhouse Gas Equivalencies).
  • Intensity: CO₂e per active user, per user-day, per million output-equivalent tokens and per gross billed dollar (gross_amount). The export aggregates usage by user, model and day: it has no request count, hence the user-day as the usage unit.
  • Trend: day-by-day cumulative total of the last month of the period. The end-of-month projection adds a forecast for each remaining day to the month-to-date total. Five methods are offered in the Calculation view. By default, the usage-based model computes each remaining day as N × p × U × I: N, distinct users over a rolling 28 days; p, activity rate by weekday, month (computed from history if it covers 13 months, otherwise July ×0.8 and August ×0.45), French public holidays and Christmas week; U, output-eq. tokens per active user; I, carbon intensity of the last 28 days' mix. N and U extend their 6-month trend, damped by 10% per month, with an optional licence cap. A P10–P90 range comes from replaying the observed errors of the last 180 days 400 times. The other methods: average pace to date, pace of the last N days, weekdays and weekends, linear trend. A % adjustment of the rest of the month accounts for a known event, and a backtest compares each method with the previous complete months. The comparison with the previous month uses the same day of the month, and only if that month is entirely within the period. The horizon can also be the end of the year: the total starts on 1 January, or on the first day of the analysed period if later, and the projection runs to 31 December.
  • Emissions day by day, week by week: color intensity proportional to the day's CO₂e, from the lowest to the highest of the period. The “Share” column splits the footprint by day of week.
  • Model lever: the current model's rows are recomputed as if the target model had processed them, with the same input, output, cache read and cache write tokens, but the target model's price ratios, δ/ε convention and FE_token. Only models already in the export are offered. Quality or verbosity differences between models are not modeled.
  • Uncertainty range: minimum and maximum among the sensitivity variants (FE_token × low and × high, Boris's calculator with each electricity mix, δ/ε convention flipped when it is only set by default). Same logic as control C6, applied to the filtered scope.

Limites

  • Les résultats sont des ordres de grandeur : l'énergie par token, le mix électrique et la convention de l'export ne sont pas publiés.
  • Les ratios de prix reflètent aussi la marge, le stockage et la stratégie commerciale ; ils ne mesurent pas l'énergie.
  • La remise automatique et le palier long contexte ne sont pas identifiables ligne par ligne.
  • L'agrégation journalière masque la surface utilisée (IDE, CLI, agent) et la structure des sessions.
  • Plusieurs facteurs de la table sont des hypothèses ou des valeurs rondes ; ils sont signalés dans la vue Calcul.
  • Results are orders of magnitude: energy per token, the electricity mix and the export convention are not published.
  • Price ratios also reflect margin, storage and commercial strategy; they do not measure energy.
  • The automatic discount and the long-context tier cannot be identified row by row.
  • Daily aggregation hides the surface used (IDE, CLI, agent) and the session structure.
  • Several factors in the table are assumptions or round values; they are flagged in the Calculation view.
